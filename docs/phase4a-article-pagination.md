# PrideDesk 4A 기사 목록 pagination

기준 commit: `71090c0ff81b2f978604ad2776a28c97d3c67631`. 운영 원고를 읽거나 수정하지 않고 동일한 가상 데이터와 실제 SQLite migration 스키마로 검증한다.

## 기존 의존성

- 관리자: 전체 기사 배열로 상태별 6개 카드 집계, 학생 ID 부분 검색, 상태/유형/제출일 필터. 별도 정렬 UI 없이 최근 수정 순서였다.
- 학생: 내 기사 전체 목록 및 홈의 자유 기사 목록이 같은 배열을 사용했다. 과제 진행률/작성하기는 과제 응답의 articleId를 사용하므로 전체 기사 배열이 필요하지 않다.
- 사진 업로드: 전체 배열을 select 옵션으로 만들었다. 이제 별도의 picker 응답을 검색/페이지 단위로 받는다.
- 삭제 확인은 현재 방문한 기사 메타데이터를 사용한다. 상세는 ID로 직접 조회하며 저장/제출/삭제 후 목록 집계 캐시를 무효화한다.
- 다른 활성 기사 선택 UI는 과제의 articleId 직접 열기뿐이다. legacy/mock 파일은 삭제하거나 개편하지 않았다.

## API / 정렬 / 호환성

`GET /api/native/articles?summary=1&page=1&limit=20`

응답: `{items, nextCursor, limit, stats?: {total, byStatus}, campaigns?: [{id,name}]}`.

- 기본 20개, 최대 50개. 범위 밖/소수/잘못된 limit은 400. limit/cursor/검색/필터 parameter만 보내도 pagination 경로를 사용한다.
- 정렬은 `updated_at DESC, id DESC`. 이후 페이지에는 nextCursor를 그대로 전달한다. `page=2` 등 숫자 offset은 지원하지 않는다.
- offset의 앞쪽 삽입에 따른 이동·중복과 깊은 페이지의 건너뛰기 비용을 피하기 위해 keyset cursor를 선택했다.
- cursor에는 버전, 조회 조건/사용자 범위, 마지막 수정 시각+ID, 첫 조회 시각 상한을 포함한다. 조건 변경/다른 사용자 cursor는 400. SQL 권한 조건은 cursor와 별개로 매번 서버 session에서 적용한다. cursor는 인증 토큰이 아니며 서명에 권한을 의존하지 않는다.
- 첫 조회 이후 새로 작성/수정된 기사는 진행 중인 목록의 앞쪽에 끼워 넣지 않는다. 기존 기사가 수정되면 이전 버전을 보관하는 DB snapshot은 아니므로 그 기사가 현재 탐색에서 빠질 수 있다. 새로고침은 조건을 유지하고 첫 페이지에서 최신 목록을 다시 읽는다. 완전한 시점 일관성을 주장하지 않는다.
- 본문/편집본/피드백/revision은 목록에 포함하지 않는다. 기존 130자 미리보기와 단어 수는 현재 페이지 원고에서 계산한다. 상세 API는 그대로 유지한다.
- parameter 없는 기존 목록과 `summary=1` 단독 요청은 이전 클라이언트 호환용으로 유지한다. 새 프런트에는 전체 목록 요청 경로가 없다. 구 Worker가 배열 응답을 반환하면 새 프런트는 전체 배열 fallback을 사용하지 않고 업데이트/재시도 안내를 표시한다.
- 호환 경로 제거 조건: production 전환 및 1시간 정적 캐시 만료 이후 구 프런트 사용/rollback 필요가 사라졌음을 확인한 후 별도 변경에서 제거. 이번 PR은 기존 클라이언트를 강제로 깨뜨리지 않는다.

## 검색 / 필터 / 집계

- q: 한글/영문 제목, 작성자 ID, 과제 배부 당시 저장된 작성자 이름, 과제명 부분 검색. 자유 기사는 기존처럼 ID를 작성자 정보로 사용하며 Google roster를 조회하지 않는다.
- author: 작성자 ID/저장된 이름 부분 검색. status/type/campaign은 정확히 일치, `campaign=free`는 자유 기사, date는 기존 UTC 제출일 필터.
- q/author는 trim, 빈 문자열은 필터 없음, 최대 200자. `%`, `_`, 역슬래시는 LIKE에서 문자 그대로 처리한다. 모든 값은 bind parameter이며 SQL 정렬/열을 사용자 문자열로 구성하지 않는다.
- 상태 집계는 현재 검색/유형/작성자/과제/날짜/권한 범위에서 상태 필터만 제외한다. 선택 상태의 total은 해당 상태 건수다. 따라서 다른 상태 버튼도 의미 있는 건수를 표시한다.
- 첫 조회/검색·필터 변경/변경 작업 이후에만 상태 GROUP BY와 과제 선택지를 읽는다. 다음/이전 페이지는 `stats=0`으로 반복 집계를 피한다. 과제별 건수는 화면에서 사용하지 않으므로 추가하지 않았다.
- 학생의 목록/집계/과제 선택지/picker 모두 자신의 기사로 제한한다. 학생 내부 메모 allowlist, Origin/CSRF/session/Drive 권한과 no-store는 유지한다.

## UI / race / picker

- 기존 카드·검토 큐·custom select 스타일을 유지한다. 이전/다음/범위/새로고침만 추가한다. 좁은 화면에서는 pagination 버튼을 줄바꿈한다.
- 검색/작성자 입력은 300ms debounce. 입력 즉시 이전 요청을 AbortController로 취소하고 sequence를 갱신한다. 늦은 응답, debounce 중 응답, 상세 화면으로 이동한 후의 응답이 최신 화면을 덮어쓰지 않는다.
- 화면 전체를 잠그지 않는다. 페이지 이동 중 기존 행과 다른 메뉴를 유지하고 페이지 버튼만 잠근다. 오류는 재시도를 제공한다.
- 컨트롤러가 검색어/필터/cursor 이력을 보관하여 상세→목록 및 같은 작업 중 메뉴 왕복 시 유지한다. 브라우저 새로고침까지 저장하는 별도 상태 저장소는 추가하지 않았다.
- 학생 홈은 과제 영역과 자유 기사 페이지를 독립 로드한다. 사진 목록도 독립 로딩을 유지한다.
- 사진 선택은 같은 권한/검색/cursor 구현의 `picker=1` 경로를 사용하며, D1에서도 원고를 읽지 않는다. 검색 결과 20개씩 이전/다음으로 선택한다. 결과 갱신 중에는 기존 선택을 비우고 선택 컨트롤을 잠근다. 검색/페이지 버튼은 form submit을 발생시키지 않는다.

## 성능 측정

가상 기사 100개, 동일 수정일, 원고 약 12KB/개. 아래는 비압축 JSON이며 운영 수치가 아니다.

| 항목 | 3차 | 4A |
|---|---:|---:|
| 첫 목록 D1 query | 1 (전체 목록) | 3 (목록 1 + 상태 집계 1 + 과제 선택지 1) |
| 검색 query | 0 (클라이언트; 제목 검색 없음) | 3 |
| 필터 query | 0 (클라이언트) | 3 |
| 다음/이전 페이지 query | 미지원 | 1 |
| picker query | 전체 목록 공유 | 1, 본문 미조회 |
| 첫 목록 response bytes | 53,401 | 8,718 |
| 다음 페이지 response bytes | 미지원 | 8,656 |

초기 HTTP 요청 수는 관리자 session+목록 2회, 학생 session+과제+자유 목록 3회로 유지된다. D1 쿼리 횟수는 증가하지만 전체 원고 전송과 브라우저의 전체 배열 필터링을 제거한다. 매번 전체 데이터의 브라우저 보관이 필요한 구조를 더 이상 사용하지 않는다.

학생 목록 실행계획은 `native_articles_by_student(student_id, updated_at)` 및 assignment의 기존 UNIQUE/PK 인덱스를 사용한다. id 동점 정렬에는 임시 B-tree가 사용된다. 전체 관리자 목록/부분 문자열 검색에는 스캔·정렬 비용이 남으므로 query 수 감소 또는 상수 DB 비용을 주장하지 않는다. 이번 자료로 production index 추가 필요성이 입증되지는 않아 schema/index/migration을 추가하지 않았다. 실제 규모에서 지연이 확인되면 실행계획과 rows_read를 기준으로 별도 검토한다.

## 배포 / 후속

merge 후 **Worker 먼저 → Vercel** 순서가 필요하다. 새 프런트는 객체형 page 응답에 의존한다. D1 migration은 없다. GitHub Pages archive 코드는 변경하지 않았다.

4B 후보는 별도 요구사항에 따른 thumbnail/이미지, 접근성, SEO이며 이번에 구현하지 않는다. 대규모 목록에서의 DB 실행시간/rows_read 실측과 호환 API 제거도 별도 검토 항목이다.
