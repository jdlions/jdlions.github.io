# 사진 관리 복구 및 휴지통

## 확인한 원인과 표시 방식
- 실제 관리자 토큰의 Drive metadata/original/thumbnail 요청은 HTTP 404였지만 같은 파일의 Drive 웹 원본과 비공개 `/preview` 뷰어는 정상 표시됐다. 404만으로 파일 삭제를 판단하지 않는다. 앱별 접근 범위와 Drive 웹 접근은 다를 수 있다.
- 관리자 원본 열기/다운로드는 기존 Drive 웹 인증·권한을 사용한다. 썸네일 프록시를 우선 사용하고 읽을 수 없으면 관리자에게만 인증된 `/api/photos/:id/preview`를 통해 Drive 비공개 뷰어를 표시한다. 다른 scope, 토큰, 공유 권한은 추가하지 않는다.
- Drive 썸네일 요청의 `redirect:error`는 Workers 런타임에서 지원되지 않는다. `manual`로 바꾸고 모든 3xx를 거절한다. 허용 호스트·이미지 MIME·1MiB 상한은 유지한다.
- 기존·신규 사진의 Drive 웹 원본 및 비공개 뷰어는 사용자가 실계정으로 확인했다. 관리자 토큰의 직접 이미지 바이트 조회는 여전히 해당 파일에서 404이므로 성공으로 보고하지 않는다. 실제 이미지 바이트/MIME/상한/리디렉션은 격리된 Workers 테스트로 검증한다.

## 휴지통
`0014_photo_trash.sql`은 사진에 is_deleted(기본 0), 삭제/복구 시각 및 작업자 FK만 추가한다. 원본 Drive 파일, 소유자, 기사 연결, 검토 상태와 기존 메타데이터는 변경하지 않는다. 추가 인덱스·외부 저장소는 없다.

관리자 DELETE `/api/photos/:id`는 기존 Origin/CSRF 검사와 `사진 삭제` 확인을 요구한다. POST `/api/photos/:id/restore`, GET `/api/photos/trash` 역시 관리자 전용이다. 조건부 UPDATE로 중복 요청이 기존 작업 시각을 덮어쓰지 않는다. 가장 최근 삭제·복구 작업자/시각을 보존한다. 일반 목록·집계·상태 변경·내용·원본·미리보기·다운로드 API에서 삭제 사진을 제외한다. 휴지통에서는 이미지를 자동으로 요청하지 않는다.

Drive 파일의 ACL은 그대로이므로 이미 알고 있는 Drive URL을 Drive에서 여는 권한까지 취소하는 기능은 아니다. PrideDesk의 삭제 사진 API 접근은 차단된다. 복구 후 기존 기사 연결이 다시 표시된다.

## 적용 및 복구
1. PR CI와 실계정 읽기 확인을 마친다. 운영 사진 삭제/복구 테스트는 하지 않는다.
2. 운영 D1 식별자·main·ledger 확인 후 SQL export를 비공개 로컬 경로에 보관하고 격리 SQLite 복원·무결성·기존 데이터 보존을 검증한다.
3. 미적용 항목이 0014 하나인 경우에만 수동 적용한다. 실패/예상 밖 상태에서는 중단하며 재실행·자동 롤백하지 않는다.
4. ledger/FK/기존 레코드 수를 확인하고 PR merge 후 기존 운영 배포 파이프라인으로 Worker → 같은 commit Vercel → 읽기 smoke를 수행한다. 자동 migration 승인 목록은 변경하지 않는다.
5. 애플리케이션 롤백은 이전 Worker/frontend로 수행할 수 있다. 추가 컬럼은 남겨 둔다. 운영 DB 복원이나 컬럼 제거는 별도 승인 없이는 실행하지 않는다. 구 Worker는 소프트 삭제 상태를 모르므로 롤백 시 삭제 사진이 다시 보일 수 있다.

## 검증
관련 Node/실제 workerd D1 테스트, 관리자/학생 권한·CSRF·IDOR·중복 삭제/복구·메타데이터 보존, Chrome/Edge 390/820/1440 UI/키보드 확인. 원본 업로드 구현과 OAuth scope는 변경하지 않는다.
