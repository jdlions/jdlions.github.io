# 학생 공통 가입 코드와 기존 회원 보존

## 로그인/가입 흐름

- 기존 회원은 코드 없이 기존 `Members.login` 경로로 로그인한다. Google sub와
  검증된 학교 이메일을 함께 조회하며, 미연결 회원만 이메일 일치 후 기존 ID에
  sub를 연결한다. 역할/기수/active/기존 원고·과제·편집 기록을 덮어쓰지 않는다.
- inactive, 이메일/sub 충돌 또는 복수 레코드 충돌은 신규 가입으로 넘기지 않는다.
  교사는 계속 관리자 수동 등록 대상이다. 초기 editor 보호 trigger도 유지한다.
- 미등록 학교 Google 계정만 `/signup/`으로 간다. OAuth Code/PKCE/state/nonce,
  JWT 서명/aud/issuer/hd/email_verified/at_hash 검증은 유지한다. People/Contacts와
  검색 연결/추가 OAuth 동의는 제거했다. 일반 로그인 scope는 openid/email/profile/
  기존 drive.file이며 검색을 위한 include_granted_scopes도 제거했다.
- 가입 대기 상태는 전용 `__Host-lp_signup` AES-GCM 쿠키(최대 10분,
  Secure/HttpOnly/SameSite=Lax/Path=/)로 보관한다. 인증된 identity와 Google token은
  브라우저 JS/로그/응답에 제공하지 않는다. 이 쿠키는 일반 세션이 아니며 기사,
  관리자 API 등 기존 보호 API를 통과하지 못한다. 완료/로그아웃/기존 회원 로그인 시 지운다.
- POST 가입에서 pending 인증·기존 회원 상태·Origin/CSRF·시도 제한·학생 정보·코드를
  다시 검증한다. 학생 역할/active는 서버가 고정한다. body의 role/email/sub/cohort 등
  신원/권한 필드는 받지 않는다. 최종 INSERT는 설정 version과 활성 상태를 다시
  조건 검사하므로 코드 교체/중지와 가입 완료 사이의 경쟁 조건도 차단한다.
- members의 기존 email/sub 및 `(cohort,student_number)` UNIQUE 제약을 사용한다.
  중복 동시 요청은 한 회원만 만든다. 사전 등록과의 경쟁도 기존 레코드를 덮어쓰지 않는다.

## 이름·학번·기수

- Google 표시 이름의 `5자리 학번 + 이름`만 분리한다. 6자리 이상 숫자 접두사,
  예외 표시 이름은 학번을 추측하지 않고 수동 확인하도록 한다.
- 현재 학번은 이메일 뒤 숫자에서 추출하지 않는다. `hYYxxxxx@joongdong.hs.kr`의
  입학 연도 `20YY`에서 1990을 빼 기수를 정하고, KST 학년도−입학연도+1과 현재
  학번 첫 자리를 비교한다. 일치하지 않으면 가입을 거부하고 정보 확인을 요청한다.
- 이메일 형식/입학 연도/학생 학년(1~3)을 확인할 수 없으면 관리자 수동 등록으로
  안내한다. 기수 임의 선택이나 예외 자동 승인은 없다. 이름/현재 학번은 학생이
  확인·수정할 수 있으며 확인 checkbox와 서버 검증을 모두 거친다.
- 저장된 기존 회원 기수는 변경하지 않는다. 재로그인 시 검증된 Google 표시 이름의
  이름이 등록 이름과 같고, 새 학번의 학년이 저장 기수와 현재 학년도에 맞을 때만
  학번 갱신 제안을 한다. 학생이 명시적으로 확인하기 전에는 DB를 바꾸지 않는다.
  이름/기수가 충돌하면 관리자 확인을 안내하며 자동 덮어쓰지 않는다. 확인 후에도
  member ID/sub/기수/이력은 유지하고 auth_version만 증가시켜 오래된 세션을 취소한다.
- KST 3월 1일 활동 기수 계산, 3학년 신규 배정 제외, 과거 이력/로그인 보존,
  로그인 전 과제 대상 연결은 기존 PR59 로직을 재사용한다.

## 관리자가 코드 설정/회원 차단

회원 관리 → **학생 공통 가입 코드 설정**을 펼친다(초기 진입에 추가 요청 없음).
관리자가 처음 코드를 직접 정하고 저장 후 셀프 가입 허용을 켠다. 구현자가 초기
코드를 정하지 않았으며 migration 기본값은 미설정/비활성이다. 새 코드는 앞뒤
공백을 제외한 12~128자이며 추측하기 어려운 무작위 문자열을 권장한다. 앞뒤 공백은
검증 때도 동일하게 제거하고 대소문자/중간 공백은 그대로 구분한다.

DB에는 난수 16바이트 salt와 PBKDF2-SHA256 100,000회/256bit 결과만 저장한다.
평문/해시는 GET에 포함하지 않는다. 코드를 바꾸거나 허용을 끄더라도 기존 회원
로그인에는 영향이 없다. 코드 저장은 version 기반 낙관적 잠금으로 충돌을 알린다.

검증된 Google sub를 SESSION_SECRET으로 HMAC한 계정별 bucket에 15분당 5회,
전체 15분당 100회 제한을 D1 원자 증가로 적용한다. 새 브라우저/임시 쿠키를 받아도
같은 계정 제한은 유지된다. 코드 시도 기록에 평문 sub/IP/이메일/코드는 남기지 않는다.
각 bucket은 다음 window에 덮어써서 재사용하며 별도 예약 작업은 없다.

기존 회원 수정의 비활성/재활성 기능을 사용한다. 매 보호 요청이 D1 active와
auth_version을 확인하므로 차단 즉시 기존 세션도 거부하며 재가입으로 우회하지
못한다. 물리 삭제는 제공하지 않는다. `최근 가입순` 정렬에서 가입 일시·학번·기수·
학교 이메일·상태를 확인한다. 과거 기수까지 보려면 활동 범위를 전체 회원으로 고른다.

## DB 영향과 운영 적용 전 절차

`0011_student_signup.sql`은 두 신규 테이블만 추가한다:

- `member_signup_code`: singleton hash/salt/활성/version/변경 시각/변경 교사 ID
- `member_signup_attempts`: HMAC bucket/window/횟수

기존 migration 수정, 기존 업무 테이블 변경/초기화/일괄 UPDATE, 신원/소유권 변경,
새 유료 리소스는 없다. 자동 migration 승인 목록에 추가하지 않았으며 배포 정책은
미적용 0011이 있으면 수동 승인 필요로 중단한다. 안전장치를 우회하지 않는다.

**이번 PR은 merge/production deploy/production migration을 하지 않는다.**
별도 운영 승인 이후 권장 순서는 다음과 같다.

1. 정확한 production D1 식별자·ledger·Time Travel bookmark·주요 테이블 건수를
   읽기 전용으로 기록하고 미적용 migration을 확인한다. 다른 항목이 있으면 중단한다.
2. 승인받은 0011만 적용/ledger 기록 후 신규 테이블의 코드 미설정·enabled=0 및
   기존 데이터 건수/외래 키 무결성을 확인한다. 기존 Worker와 호환되는 추가 테이블이다.
3. 동일한 merge commit의 Worker → Vercel 순으로 배포하고 일치 여부를 확인한다.
4. 기존 editor/학생 로그인과 기존 데이터, 신규 가입 UI를 확인한다. 그 다음 관리자가
   최초 코드를 설정/허용하고 학생에게 공유한다. 코드 미설정 상태에서는 가입되지 않는다.
5. 실패 시 임의 SQL/롤백/재실행 없이 중단한다. 이미 가입한 회원은 코드 중지로
   취소되지 않는다. 부적절한 가입은 기존 회원 비활성화를 사용한다.

## Preview와 검증 범위

기존 전용 Worker/D1/고정 Vercel Preview를 그대로 사용한다. DB 이름에 남은
member-search는 기존 리소스 이름일 뿐 검색 API가 아니다. 운영 D1은 연결하지 않는다.
PREVIEW_MODE가 있으면 업무 쓰기를 차단하고 세션/회원 읽기, 가입, 관리자 코드
설정만 허용한다. Google callback은 PREVIEW_ADMIN_EMAIL 또는 명시적으로 지정한
PREVIEW_STUDENT_EMAIL만 받는다. 테스트 계정을 임의 생성/등록하거나 범위를 넓히지 않는다.
0011도 격리 Preview에만 적용 가능하며 production에는 별도 승인이 필요하다.

관리자는 기존 고정 Preview의 회원 관리/코드 설정 UI를 확인할 수 있다. 실제 신규
학생 Google 가입은 테스트 학생 이메일의 사전 지정과 관리자의 테스트 코드 설정이
필요하다. 구현자의 임의 코드 설정이나 학교 연락처 조회는 하지 않는다.
브라우저 fixtures와 서명된 mock Google JWT/SQLite/실제 workerd 검증은 실계정
Google 가입 완료와 명확히 구분해 보고한다.
