# PrideDesk 3차 데이터/API 성능 최적화

기준: f975d54d9747b1acfc22e8df28bdb434eed55a96. 운영 학생 데이터 없이 같은 가상 데이터로 비교했다.

## 화면 의존성과 초기 요청

| 화면 | 이전(session 포함) | 이후 | 첫 데이터 표시 조건 |
|---|---:|---:|---|
| 관리자 기본 기사 큐 | 5 | 2 | session → 기사 요약 |
| 학생 기본 대시보드 | 4 | 3 | session → 과제 또는 기사 중 먼저 완료한 영역 |
| 관리자 사진 직접 진입 | 5 | 2 | session → 사진 |
| 관리자 신문 발행 직접 진입 | 6 | 2 | session → publications |

과제 관리에서만 과제 목록을 읽고, 학생 명단은 새 과제 작성 버튼을 누를 때 읽는다. 사진 업로드의 기사 선택은 필요 시 기사 요약을 로드한다. 같은 데이터 요청은 화면 이동 간 공유하며 실패한 요청만 다시 시도한다. 과제/기사 응답이 늦게 도착해도 이미 연 편집기를 다시 그리지 않는다. 상세 직접 링크는 목록 전체를 먼저 읽지 않는다.

## 목록과 상세

새 프런트는 GET /api/native/articles?summary=1을 사용한다. 배열 형태와 목록 메타데이터는 유지하며, draftPreview(130자)와 wordCount로 기존 미리보기/단어 수를 유지한다. 본문, 편집본, 피드백과 revision은 상세에서 읽는다. 동시 상세 요청도 합친다.

기존 프런트의 1시간 정적 캐시와 배포 순서 호환을 위해 query 없는 기존 목록 응답은 유지한다. 구 Worker도 summary query를 무시하고 기존 응답을 주므로 신 프런트는 fallback으로 읽을 수 있다. 새 summary 경로는 학생 viewer allowlist를 그대로 통과한다.

20개 가상 기사(각 원고/편집본 약 36KB), 실제 Worker 학생 HTTP JSON 직렬화 기준:

| 항목 | 이전 bytes | 이후 bytes |
|---|---:|---:|
| 기사 목록 | 1,451,051 | 11,351 |
| 기사 상세 1개 | 72,567 | 72,567 |

비압축 JSON 크기이며 실제 운영 사용자의 성능 수치가 아니다. 요약 미리보기와 단어 수 계산을 위해 D1에서 학생 원고는 여전히 읽는다. 편집본/피드백 열과 불필요한 feedback JOIN은 summary 쿼리에서 제외한다. 파생 요약 저장을 위한 migration은 추가하지 않았다.

## D1 과제 조회

기존 캠페인별 3회 조회를 캠페인/슬롯/대상 학생의 세 집합 조회로 바꿨다. 학생 권한은 각 집합의 membership EXISTS 조건으로 제한한다. 캠페인당 별도 쿼리 및 큰 IN 바인딩 목록이 없다.

과제 API 전체(assignment instance 조회 포함): 캠페인 N개 기준 3N+2 → 4회. 10개는 32 → 4회, 빈 목록은 2 → 2회. 실제 SQLite migration 스키마로 관리자/학생/비대상 학생의 응답 내용 및 순서 일치를 테스트했다. 인덱스/schema 변경 없음.

## Timeout / 오류

- 브라우저 session: 30초
- 일반 Worker API: 60초
- 브라우저 업로드/가져오기: 180초
- Google OAuth/Classroom/Drive 메타데이터: 요청당 20초
- Google Drive 바이너리 업로드/다운로드/이미지 스트림: 요청당 120초

헤더뿐 아니라 응답 body 읽기까지 제한한다. Classroom 다중 페이지/멤버십은 여러 요청이므로 위 시간은 전체 흐름의 SLA가 아니다. 현재 Google Docs 전용 API는 사용하지 않으며 DOCX/TXT는 기존 가져오기 경로에서 처리한다. 요청 timeout은 쓰기 롤백을 의미하지 않는다. 자동 재전송하지 않고 쓰기 결과 확인 안내를 제공한다.

오류/timeout은 해당 데이터 영역의 재시도로 복구하고 다른 메뉴는 사용할 수 있다. session 확인 실패도 재확인 및 새 Google 로그인 진입을 제공한다. 학생 저장 실패 시 현재 원고/편집 화면을 유지한다. 인증·Origin·CSRF·no-store는 변경하지 않았다.

## Pagination 후속 설계

이번에는 미구현. 현재 전체 목록을 쓰는 상태별 집계, 클라이언트 검색/필터, 과제에서 상세 이동, 사진 업로드 기사 선택을 함께 전환해야 하므로 범위가 커진다.

후속으로 updatedAt+id cursor와 page size를 쓰되 상태/유형/작성자/날짜 필터를 서버로 옮기고 동일 필터에 대한 집계 응답을 별도로 제공한다. 사진 기사 선택도 검색 API로 분리한다. 검색 조건 변경 시 cursor를 초기화하고 수정/삭제 후 이동 및 중복/누락을 테스트해야 한다. 인덱스는 실제 실행계획 확인 후 결정한다.
